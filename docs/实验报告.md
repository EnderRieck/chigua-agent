# 社会网络分析 第一次作业实验报告：基于 LLM 编排的"吃瓜智能体"

## 一、示例代码分析

课程提供的 C3 示例代码（v1–v5）用一个"商家聊天机器人"演示了智能体的基本骨架：**感知（Perception）→ 决策（Decision）→ 执行（Executor）**，三个模块各自封装为类，由 `MerchantAgent` 串联。五个版本逐步加功能：

- **v1** 搭起骨架，从 CSV 读取商品表，靠标点判断是否为问句，不含任何模型。
- **v2** 升级决策模块，用关键词规则识别"问候 / 问答 / 购物 / 闲聊"四类意图。
- **v3** 把数据搬进 SQLite（`builddb.py` 用 pandas 合并三家平台的 CSV），决策模块开始"既决定做什么，也准备数据"。
- **v4** 把颜色、预算、商家的抽取抽成独立的 `parsers.py`，加入多步放宽的规划策略：严格条件搜不到就逐步放宽。
- **v5** 增加持久化记忆（`memory_store.py` 把用户偏好存进同一个数据库）和偏好管理指令，决策时把记忆与当前输入合并成最终查询。

示例的价值在于把"意图识别、知识检索、规划放宽、记忆"四种能力分层叠加，每层只改一个模块。局限也很明显：所有理解都靠关键词和正则，换一个领域就要重写规则；没有外部信息源，无法处理开放问题。本次实验正是沿着这个骨架，把规则换成大模型，把本地数据库换成多平台实时检索。

## 二、吃瓜智能体的设计

**任务定义。** 用户给出一个时事热点或网络事件，智能体自动检索新闻、微博、知乎、小红书、X 五类信息源，输出一份区分事实、传闻、观点并标注来源的"吃瓜报告"。

**整体结构。** 仍然是三段式，但每段的实现方式变了：

1. **规划员（Planner，对应感知与决策）。** 用 Grok 读取用户问题、对话历史和已有证据索引，输出一份 JSON 检索计划：规范化事件名、4–7 条跨平台查询及理由、本次要回答的核心问题。追问时它会判断是否需要新检索。
2. **采集（Gather，对应执行）。** 工具注册表把计划里的查询并发执行。每个平台一个适配器，返回统一格式的条目，全部写入**证据库**并编号为 [E1]、[E2]……，按链接去重。
3. **分析员（Analyst）。** Grok 拿到证据摘要后流式撰写报告，中途可通过 function calling 追加检索（最多 4 轮），例如发现缺官方回应就补一次 `web_search`，发现某个知乎问题值得深挖就调 `zhihu_question_answers`。报告固定为"一句话吃瓜 / 时间线 / 各方说法 / 各平台舆论场 / 争议焦点 / 吃瓜指南"六节，每条事实后必须带 [E#]，系统再根据引用自动生成来源列表。

**信息源与降级链。** 这是设计中最花功夫的部分，因为四个社交平台都没有官方搜索 API：

| 平台 | 主路径 | 降级 |
|---|---|---|
| 新闻 | DeepSeek Search / Fetch API | — |
| 微博 | 本人 Cookie 直连热搜接口与桌面搜索页（解析 HTML） | 公开热搜镜像 → DeepSeek `site:weibo.com` |
| 知乎 | 本人 Cookie + 本地实现的 x-zse-96 签名直连搜索与回答接口 | DeepSeek `site:zhihu.com` |
| 小红书 | 本地运行的 xiaohongshu-mcp（浏览器自动化，MCP 协议调用） | DeepSeek `site:xiaohongshu.com` |
| X | xAI Responses API 的服务端工具 `x_search` | Live Search → DeepSeek |

每级降级都把原因写进证据说明，分析员据此判断可信度；X 的两条模型侧链路都要求接口返回真实引用，否则视为未联网并降级，避免模型编造帖子。

**与示例代码的对应。** 证据库相当于 v5 的记忆，但记的是本轮检索到的事实而非用户偏好；规划员的"是否需要新检索"相当于 v2 的意图识别；分析员的追加检索相当于 v4 的多步放宽；工具注册表相当于 v3 把"准备数据"从决策里拆出来。

## 三、安装与配置

环境用 pixi 管理，Python 3.12，依赖 openai、httpx、rich、mcp、prompt-toolkit、pytest。

```bash
cd 吃瓜智能体 && pixi install && cp .env.example .env
```

`.env` 必填两项：Grok 的 Key 与中转站地址（`XAI_BASE_URL` 填到 `/v1` 为止，模型名以中转站列表为准）、DeepSeek 的 Key。可选项：微博与知乎从浏览器开发者工具复制的本人 Cookie；小红书需先下载 xiaohongshu-mcp 的 macOS 二进制，扫码登录后以 `-headless=false` 启动，再把 `XHS_MCP_URL` 指向 `http://localhost:18060/mcp`，项目内置 `pixi run xhs-login` 可直接弹出登录二维码。

常用命令：`pixi run doctor` 逐项自检 11 个配置与接口；`pixi run hot` 看双平台热榜；`pixi run ask 某事件 --save` 一次性分析并保存；`pixi run chigua` 进入交互模式，支持 `/hot`、`/dig W3`、`/sources`、`/save` 等命令和多轮追问。

## 四、实验结果

以"帮我查查华晨宇新歌"为例，规划员把这个口语化的问题规范化为事件"华晨宇新歌《不奉陪》"，拆出跨平台查询并发采集，共得到 29 条证据（新闻 14、X 7、微博 5、知乎 3），生成约 12 KB 的报告。报告做对了几件事：把 4 月上线的游戏主题曲《千万次奔向》和 10 月 25 日南京演唱会首唱的《不奉陪》区分开，避免把两首"新歌"混为一谈；指出录音室版和发行日期在证据里找不到，只能确认"现场首唱"这一事实；对"第七张还是第八张专辑""几分钟写完"等粉丝转述标注为未经工作室证实；知乎和小红书两栏如实写"本次未获取到"，并说明小红书是检索超时而非无人讨论。离线单元测试 8 项通过，覆盖参数容错、证据去重、签名算法、各平台解析。

## 五、实验收获

1. **架构比模型更重要。** 示例代码的三段式骨架完全可以承载大模型：把规则替换成"规划员输出 JSON"和"分析员 function calling"，结构几乎不用改，这说明感知-决策-执行的抽象是稳定的。
2. **证据编号是抑制幻觉最有效的手段。** 强制分析员引用 [E#]，再由程序生成来源列表，报告里每句事实都可回溯，比在提示词里反复强调"不要编造"管用得多。
3. **降级链和超时预算决定了可用性。** 实际运行中遇到的问题几乎都在边界：中转站不支持某个接口、小红书关键词带空格会卡死、X 搜索偶尔超过 80 秒、桌面 Cookie 对手机端接口无效。每个都靠"给原因、换路径、如实标注"解决，而不是让整次分析失败。
4. **非官方接口的边界要守住。** 本项目只使用公开镜像、公开接口、用户本人的 Cookie 和本人扫码登录的会话，不伪造访客身份绕过平台校验；Cookie 等同密码，只存本地并写入 `.gitignore`。
5. **平台内容生态确实不同。** 同一首新歌，微博几乎一边倒地刷"爽""解压"，工作室、超话和音乐博主复读同一套文案；知乎没有任何针对这首歌的问题或长文，搜到的全是旧专辑话题；X 上是海外粉丝搬运工作室文案并配英文字幕，互动只有个位数；豆瓣小组反而出现"赶工、气氛组"的不同意见。多平台并行采集本身就是对社会网络中信息分层传播的一次观察：同一事件在不同社区里的热度、立场和讨论深度差异极大，只看一个平台很容易得出片面结论。
